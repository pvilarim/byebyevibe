# Evaluation: LifeOS — AI harness / constitutional layer for agent sessions

| Field | Value |
|-------|--------|
| **Date** | 2026-08-11 |
| **Evaluator** | Explore session `/opsx:explore` (Cloud Agent, Claude Code) |
| **Candidate** | [LifeOS](https://github.com/danielmiessler/LifeOS) (MIT, TypeScript + Bash, Bun runtime) |
| **Decision** | **Discarded** as kit payload / constitutional layer · **Deferred** as a source of patterns |
| **Scope** | User-global harness layer (`~/.claude/`) — sdd-kit candidate, rejected; verification doctrine retained as a backlog item |

## Executive summary

LifeOS is a general-purpose AI harness that installs a constitutional layer into the user's global agent config: its own `CLAUDE.md`, a system prompt loaded via `--append-system-prompt-file`, ~16 hooks, ~50 skills, a memory tree, and an optional dashboard daemon. Its workflow is a single artifact-driven hill-climbing loop against an **ISA** (Ideal State Artifact) whose claims each name the probe that would falsify them — "the spec IS the test suite."

**Discarded** as a kit layer: the conflict is that both LifeOS and ByeByeVibe are *constitutional*. Each wants to be what defines "done", what governs source authority, and what is injected at session start. They also disagree explicitly on whether procedural instruction to an agent is architecture or debt — LifeOS's BPE doctrine would cut this repo's Task Classification Protocol as scaffolding. Layered on top: user-global vs repo scope, a delta-based change model vs a living-document model, and an install surface this repo's own permission policy denies.

**Deferred** as a pattern source: LifeOS's verification doctrine (per-claim evidence modality, temporal/cache fidelity, evidence coverage, class-sweep, restore-parity) fills a real gap in the SDD stack and is portable with **zero runtime dependency**. Same shape as the symbolic-short-term-memory carve-out in the TencentDB discard.

## Problem it tried to solve

Two problems at once, only one of which the SDD stack shares:

1. **Personal/professional intent capture** — persistent context about goals, people, and current state, so the agent does not re-learn the operator every session. Out of scope for this repo.
2. **Making "done" verifiable** — an artifact that states what done means as falsifiable claims, and refuses to close a claim without tool evidence. Directly in scope, and the reason this evaluation is not a flat discard.

### Verified facts

- **Install scope is user-global, not repo.** `Setup.md` writes `<configRoot>` = `~/.claude/` for Claude Code: `CLAUDE.md`, `LIFEOS_SYSTEM_PROMPT.md`, `settings.json`, `skills/` (~50, `copyMissing`), `LIFEOS/`, `MEMORY/`, `USER/`, `agents/`. It halts if `DetectEnv.ts` reports `isDevTree` (refuses to mutate the author's source repo).
- **Install engineering is disciplined.** Dry-run before `--apply` at every step, `copyMissing` (never overwrites populated files), `settings.json` backed up before hooks are merged additively and deduped per command, `ScanConflicts.ts` for skill-name collisions, shell-rc edit permission-gated and backed up, `Doctor.ts` for health audit. Declared rules: *"Additive, never clobbering"*, *"Permission before mutation."*
- **The Algorithm has no classifier and no phase machine.** v8.17.3 states: *"I don't classify the work into an effort tier or predict how hard to go before I start"*; *"effort tiers, predicted classes, and phrase-triggered classifiers stay dead"*; *"The 8-station byte-stable enum contract and the `AlgoPhase.ts` CLI were retired 2026-07-14; there is no phase CLI and no station ceremony of any kind."* The README's OBSERVE→…→LEARN / E1–E5 description is **stale marketing** (v8.4.0) and must not be cited.
- **The loop is ISA-centric.** Lifecycle bracket only: `phase: marking → climbing → complete`, plus a `learn` rewind (`iteration+1`) triggered by editing the body of a `complete` ISA; ~27% of runs iterate. Home: `<project>/ISA.md` for persistent things, `MEMORY/WORK/{slug}/ISA.md` for tasks. *"'Add a feature' means 'add claims that don't hold yet.'"*
- **16 completion claims with graded teeth:** `HOOK` blocks mechanically, `CHECK` is a gate the run executes and records, `SELF` is attestation watched for decay. `VerificationGate.hook.ts` grades evidence from the transcript's actual tool calls, *"not the message's wording, so rewording never passes it."*
- **No proposal-approval gate.** Human input is bounded to *"up to 3 targeted questions when the answer would change what gets built"*; a literal whole-response `proceed` accepts reasoned defaults. The gates are at close, not at entry.
- **No archive concept.** *"The changelog is git"*; the ISA carries no changelog section; on close, a claim's evidence collapses to a one-line provenance stub (commit hash, test name, probe ref).
- **Memory writes are routed and default-SKIP.** The Learning Router dispatches by type (`knowledge`→KNOWLEDGE, `incident`→`MEMORY/LEARNING/INCIDENTS/INC-YYYYMMDD-<slug>.md`, `rule`→CLAUDE.md/OPERATIONAL_RULES, `gotcha`→the skill, `state`→PROJECTS.md), with `identity`/`doctrine`/`hook`/`permission` **surfaced to the principal** rather than written.
- **Context strategy converges with `sdd-session-handoff`.** *"When a run approaches that zone (~100k), prefer closing a coherent work unit and re-entering fresh from the ISA over pushing one long session through compaction … resume reads the artifact, never the conversation."* Same mechanism, different trigger (token budget vs phase boundary).
- **BPE doctrine (`Philosophy.md`) is explicitly anti-procedural.** Operative test: *"would a smarter model make this rule unnecessary? If yes, it is scaffolding, not architecture, and it belongs cut."* Four classes of HOW survive: safety-gates, verified-gotchas (provenance required), tool-contracts, output-format-contracts.
- **Runtime surface:** Pulse dashboard on `:31337` via macOS `launchd` (optional), optional `worksweep`/`derivedsync` jobs, optional Hermes sidecar (pinned commit, device-code login), `gh` required for the Work System.
- **Install path:** `curl -fsSL https://ourlifeos.ai/install.sh | bash`, or an agent instructed to read a remote URL and execute it. No MANIFEST or checksum equivalent was found.

## Workflow comparison — explore → propose → apply → archive

| OpenSpec phase | LifeOS equivalent | Relation |
|---|---|---|
| **explore** → `research.md`, dedicated chat | No phase. The ISA's **"Not yet specified"** slot holds in-scope fog not yet stateable as a claim, graduating into claims as pursuit sharpens it; plus up to 3 targeted questions on material ambiguity | Exists as a **slot**, not a phase |
| **propose** → `proposal.md` + `design.md` + `specs/` + `tasks.md`, human review before code (**R7**) | Claim 2 — *"Done existed in writing before building"*: an ISA at the correct home, claims each naming their falsifier, plus Anti-claims (claim 3) and Out of Scope | Same write-before-build requirement; **human approval gate absent** |
| **apply** → execute `tasks.md`, tick `[x]` | `climbing`. Claim 8: no claim closes without tool evidence **of the right modality** in the same or next tool block; `CheckpointPerISC` commits every `[x]` | Convergent in form, **far stricter** on proof |
| **archive** → merge into `specs/`, move to `changes/archive/` | **No equivalent.** The ISA stays in place and becomes the thing's current state; git is the change record; evidence collapses to a provenance stub on close | **Structurally incompatible** |

Four differences carry the verdict:

1. **Delta vs living document.** OpenSpec treats a change as a reviewable delta merged into `specs/` and archived. LifeOS mutates one ISA in place and leaves history to git. Two bookkeeping models for the same object; run together, they produce two silently diverging answers to "what is done".
2. **Gate at entry vs gate at exit.** R7 blocks before code. LifeOS blocks at close, with hook-enforced gates that read the transcript rather than the prose. Different control philosophy, not different rigor.
3. **Fresh chat per phase vs one run.** `sdd-session-handoff` mandates a clean chat per phase and requires refusing `/opsx:apply` in an explore chat. LifeOS runs one window and re-enters fresh on token budget, resuming from the artifact. Convergent mechanism, opposite trigger.
4. **Task list vs claim set.** `tasks.md` is ordered work; ISA claims are falsifiable assertions with named probes, so the claim set *is* the test suite.

## Fit with the SDD stack

| Tool | Relation |
|------|----------|
| OpenSpec | **Adversarial at the process layer, neutral at the object layer.** ISA/TELOS as a personal artifact does not compete with `openspec/specs/`. But `<project>/ISA.md` as a living spec-and-test artifact competes head-on with the change→archive model, and LifeOS has no proposal-approval gate to map onto R7. The **Deferred** pattern lives here: claims-with-falsifiers is a strictly stronger shape than `tasks.md` checkboxes |
| GitNexus | **Weak overlap + routing risk.** ContextSearch is ripgrep-based, strictly weaker than a symbol graph and with no `impact` equivalent; Atlas is an asset graph over user files, not code. The risk is a global skill routing the agent to ContextSearch where R-rules require `gitnexus_impact` before editing symbols. Not the frontal overlap that discarded `code-review-graph` |
| Graphify | **Partial overlap, weaker than first assessed.** `MEMORY/KNOWLEDGE` is a typed markdown tree written by the Learning Router, not a generated concept graph; Graphify remains deterministic (AST, no LLM) where LifeOS is narrative. Overlap is in *purpose*, not in *artifact*. `[NEEDS VERIFICATION]` on the tree's real shape |
| AGENTS.md / sdd-kit | **Direct policy conflict.** Applying the BPE test to this repo: R10 survives as tool-contract, Security NEVERs and R6 as safety-gates, F7 as output-format-contract — but the **A–E Task Classification Protocol and R1 are cut as choreography**. LifeOS would delete the core of this repo's agent protocol; this repo would reject LifeOS's undeclared, judgment-based spend as unauditable. Both positions are coherent; they are not co-installable |
| `sdd-session-handoff` | **Convergent, not adversarial.** Both prefer closing a work unit and re-entering from the artifact over compaction. Worth citing as independent corroboration of the spec |
| `.claude/settings.json` | **Mechanical conflict.** The repo denies `Bash(curl * | bash)` and `Bash(curl * | sh)` — the documented LifeOS install command. The repo's single `PreToolUse:Bash` hook (graphify nudge) would share the `additionalContext` channel with ~16 global LifeOS dispatchers |

## Expected vs observed gains

| Advertised gain | Assessment |
|-----------------|------------|
| Verifiable "done" — every claim names its falsifier, evidence of the right modality, "should work" is forbidden | **Real, and stronger than anything in the stack.** R6 + Probity `enforceTdd` + `sdd-gates` cover a fraction. This is the gain worth capturing |
| Incident-derived verification rules (modality, temporal, cache, coverage, class-sweep, restore-parity), each citing a dated incident ID | **Real and portable.** Meets this repo's own provenance bar — every rule points to a reproduction, which is precisely what `Philosophy.md` demands of a `verified-gotcha` |
| Persistent cross-session context (Cortex / MEMORY) | **Not transferable, and partly a non-goal.** Better disciplined than TencentDB (routed, default-SKIP, human-surfaced for identity/doctrine), but recall at session start still carries no provenance marker, so R2 ranking and R3 gap-marking degrade |
| Harness-agnostic, no migration required | True for install; **false for governance** — the constitutional layer is the whole product, and it is not partial-installable |
| Non-forked second look (a fork inherits build context and defends its own code) | **Genuine insight**, sharper than the kit's current post-apply review skills. Cheap to adopt as a rule |
| Adaptive spend without effort tiers | Coherent within LifeOS's epistemology. Unauditable under R1/R8 — there is no declared class to review a decision against |
| ~50 bundled skills | Unassessed (`[NEEDS VERIFICATION]`); irrelevant to the verdict, which turns on the constitutional layer |

## Alternatives already in the stack

1. **Change-as-delta with a human gate** — `/opsx:propose` + R7, reviewed before code exists.
2. **Deterministic graphs** — GitNexus (code) and Graphify (concepts) answer structure questions from AST, not narrative.
3. **Artifacts as memory** — `openspec/specs/` and `changes/` carry decisions across sessions in git, diffable and reviewable.
4. **Explicit phase handoff** — `sdd-session-handoff` already treats a clean context as the mechanism.
5. **Curated operator preference** — `sdd-skill-guidance`: offer-only, human decides, result is a versioned skill.
6. **Fail-closed CI** — `sdd-gates` (`openspec validate --all --strict`, `verify-task-patterns.sh`, OSV) plus optional Probity `enforceTdd`.

## Decision and re-evaluation conditions

**Decision: Discarded** for `sdd-kit`, `openspec/infra.md`, and the normative SDD pipeline. Personal opt-in outside the explore/propose/apply phases is not forbidden, but is neither documented nor supported by the kit — and would require a separate agent profile, since the layer is user-global.

**Decision: Deferred** for the verification doctrine as an SDD pattern, with no runtime dependency on LifeOS. Backlog shape below.

**Conditions to reopen the runtime:**

- A **repo-scoped**, versioned install with verifiable payload integrity (checksums or commit pinning), rather than a remote fetch executed by an agent.
- A recall mode that **marks provenance** on injected memory, so R2 ranking and R3 gap-marking stay enforceable — same condition set on TencentDB.
- The Algorithm exposed as an **optional layer that delegates** classification and the pre-code gate to the host repo's protocol, instead of replacing the constitution.
- `LIFEOS_SYSTEM_PROMPT.md` read and assessed; the current discard rests on an unread constitutional file, which is a gap in this evaluation, not a finding against the file.
- Scope restricted to non-overlapping subsystems (ISA, Pulse). `MEMORY/KNOWLEDGE` and Atlas stay out by purpose-overlap with Graphify and GitNexus.

**Deferred backlog (independent of adoption):**

- **Claim-with-falsifier as a task shape** — evaluate an optional `tasks.md` variant where an item names the probe that would falsify it, extending `sdd-task-patterns`.
- **Evidence modality table** — a rule that a claim closes only on evidence of the matching kind (file→Read, code→Grep, HTTP→`curl -i`, deploy→live probe, appearance→pixels actually viewed), with `"should work"` banned.
- **Non-forked reviewer rule** — a forked subagent inherits build context and defends its own code; an independent second look must run non-forked. Directly applicable to `correctness-review` / `security-reviewer` invocation.
- **Class-sweep** — a defect recognized as an instance of a class does not close until one grep enumerates every sibling, each fixed or tombstoned.
- **Ask-fidelity ledger** — every explicit ask met, skipped with a stated reason, or surfaced; any ✗ blocks completion.

Each is a candidate for its own `/opsx:propose`; none requires installing LifeOS.

## Final positioning

```
ByeByeVibe   →  change as reviewable delta; human gate BEFORE code; specs are the merged truth
LifeOS       →  one living artifact; hook-enforced gates AFTER code; git is the truth
             →  runtime discarded (two constitutions, one session)
             →  verification doctrine deferred — portable, zero runtime dependency
```
