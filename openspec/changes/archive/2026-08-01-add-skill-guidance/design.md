# Design — add-skill-guidance (v1, text-only)

## Context

ByeByeVibe's kit already uses skills as a delivery mechanism (`openspec-help` under both `.claude/skills/` and `.cursor/skills/`, shipped via `sdd-kit/templates/` + MANIFEST), but nothing teaches operators when a user-created skill helps versus when it is pure token cost, and no surface detects domain-density during conversation. Explore merge `explore-skill-guidance` (D1–D10) settled the pedagogy: agent-side detection, offer-only suggestion with a fixed three-part message, rule of three at archive, hygiene at creation, and all monitoring tooling deferred to v2.

Constraints that shape this design:

- **Upstream ownership:** `/opsx:explore|propose|apply|archive` commands and `openspec-*` workflow skills are generated by `openspec init` (OpenSpec ALL_WORKFLOWS). The kit owns only `/opsx:help` + `openspec-help` (MANIFEST comment: "kit-owned; not OpenSpec ALL_WORKFLOWS"). The installer has no APPEND/patch merge mode (`install.sh` supports COPY, MERGE = keep-dest, MERGE_PROFILE for AGENTS.md), so the kit cannot patch upstream-generated files in installed repos.
- **Hub precedent:** this repo already carries local additions inside upstream surfaces (e.g., "Session coordination" in `.claude/commands/opsx/apply.md` and `.claude/skills/openspec-apply-change/SKILL.md`). Direct edits to hub surfaces are accepted practice.
- **Kit-owned per-surface artifacts:** the only established dual-surface vehicles are skills and commands (`openspec-help` pattern), plus single-copy docs (`doc/sdd-operator-day1.md` is a kit template).
- **Non-goals (binding):** no always-on rule, no forced pre-development skill authoring, no v2 tooling (M5 metric, usage hook, `/opsx:harvest`, seed skills), max one suggestion per session.

## Goals / Non-Goals

**Goals:**

- Teach novices the skill litmus test, the skill/spec/`project.md` boundary, agent-routed creation, and the create → measure → prune lifecycle — in `doc/sdd-operator-day1.md`, narrated by `/opsx:help`.
- Make explore and propose surfaces recognize domain-density signals and answer with the standard three-part suggestion message (offer-only, ≤1 per session).
- Add the repetition confidence question (rule of three) to the archive workflow.
- Ship all guidance text dual-surface via `sdd-kit/templates/` + MANIFEST checksums.
- Record the evaluation under `doc/avaliacoes/` (methodology R5).

**Non-Goals:**

- Any new script, hook, metric, or telemetry (v2 — recorded as deferred requirements in the `sdd-skill-guidance` spec delta).
- Forking upstream OpenSpec explore/propose/archive files into the kit.
- An organizational domain-skill library (v3).
- More than one suggestion per session, or any always-on suggestion rule.

## Decisions

### D-A — Canonical text lives in a new kit-owned dual-surface skill `sdd-skill-guidance`

The full guidance corpus (detection signals catalog, standard three-part suggestion message, anti-noise cap, creation hygiene rules, staleness marker, archive question) becomes one skill shipped exactly like `openspec-help`:

- Live: `.claude/skills/sdd-skill-guidance/SKILL.md` + `.cursor/skills/sdd-skill-guidance/SKILL.md`
- Kit: `sdd-kit/templates/.claude/skills/sdd-skill-guidance/SKILL.md` + `sdd-kit/templates/.cursor/skills/sdd-skill-guidance/SKILL.md`, registered in `MANIFEST.yaml` (profiles: APP, DOCS_SPECS, HYBRID; merge: COPY) with regenerated checksums.

The skill practices what it preaches: task-based name, description of 1–2 trigger-focused sentences ("when the user repeatedly teaches domain facts / asks to create a skill…"), knowledge in the body, mode C (on demand — no always-on injection).

*Alternatives considered:* (a) always-on `.cursor/rules/*.mdc` — violates the no-always-on non-goal and charges every session; (b) kit-owned forks of upstream explore/propose files — merge-mode limitations mean the fork either clobbers upstream (COPY) or never lands (MERGE keeps dest), plus permanent drift against OpenSpec releases; (c) text only in the day-1 doc — not per-surface, fails the `sdd-install-kit` delta and gives the agent nothing to load at detection time.

### D-B — Hub explore/propose surfaces get a compact detection clause; depth stays in the skill

Add a short (~12-line) "Skill suggestion (domain-density detection)" section — signal list, the three-part message skeleton, the one-per-session cap, pointer to `sdd-skill-guidance` for hygiene — to the hub's eight explore/propose surfaces:

- `.claude/commands/opsx/explore.md`, `.claude/commands/opsx/propose.md`
- `.cursor/commands/opsx-explore.md`, `.cursor/commands/opsx-propose.md`
- `.claude/skills/openspec-explore/SKILL.md`, `.claude/skills/openspec-propose/SKILL.md`
- `.cursor/skills/openspec-explore/SKILL.md`, `.cursor/skills/openspec-propose/SKILL.md`

Same duplication pattern as the existing session-coordination sections. Installed repos get detection via the kit-owned skill (D-A) since their upstream surfaces cannot be patched; the hub gets both, which is the strongest available approximation of "kit explore and propose surfaces MUST instruct the agent" under the ownership constraint. Risk of upstream `openspec update` clobbering hub edits already exists for session coordination and is accepted (re-apply on update).

### D-C — Archive question rides the existing confidence lists

One question inserted into the archive confidence checklist: "Did anything in this change repeat a procedure or explanation from a previous change? (rule of three: 1st normal, 2nd note it, 3rd extract a skill)". Touch points: hub archive surfaces (`.claude/commands/opsx/archive.md`, `.cursor/commands/opsx-archive.md`, both `openspec-archive-change` SKILL.md mirrors) and day-1 §6 "Confidence (archive)". No new ceremony, no blocking gate — a confidence question, same register as the existing four.

### D-D — Day-1 doc gains §7 "Skills — memory beyond specs"; "Next step" renumbers to §8

New section between archive (§6) and the handoff example, covering: litmus test in plain language, skill vs spec vs `project.md` boundary, agent-routed creation ("ask the agent to create the skill; don't hand-write SKILL.md"), create → measure → prune framing with rule of three, staleness marker for volatile data, and an explicit "you do NOT write skills before starting development" line. Applied to both the live doc and `sdd-kit/templates/doc/sdd-operator-day1.md`.

Renumbering cost: "§0–§7" / "day-1 §7" references in `openspec-help` SKILL.md (live ×2 + template ×2) and `/opsx:help` commands (×2) update to "§0–§8" / "§8"; the help skill's section table gains the row for §7. These files must change anyway for the "help narrates skill guidance" requirement.

*Alternative considered:* appendix after §7 to avoid renumbering — rejected; the handoff example is deliberately the last thing an operator reads, and the section table is small enough to update atomically.

### D-E — Standard suggestion message is specified once, verbatim

The three-part message text is written once in the `sdd-skill-guidance` skill body and referenced (not re-authored) everywhere else, so wording drift cannot split the surfaces. Shape:

1. **Will:** "If we save this as a skill, future sessions recall it automatically whenever <topic> comes up."
2. **Won't:** "It does not update itself — if the law/number/method changes, you must ask to update it, or it will keep asserting stale data."
3. **Decide:** "Want me to create it? (yes / no / later)" — offer only; never create unprompted; at most one suggestion per session.

### D-F — Evaluation stub + MANIFEST bookkeeping

`doc/avaliacoes/2026-08-01-skill-guidance.md` from `TEMPLATE.md` (decision: Adopted; scope: kit guidance surfaces), plus its row in `doc/avaliacoes/README.md`. MANIFEST: two new file entries (D-A), refreshed `sha256` for the modified day-1 doc and help-skill templates via `bash sdd-kit/gen-manifest-checksums.sh`; `bash sdd-kit/gen-manifest-checksums.sh --check` is the gate.

## Risks / Trade-offs

- [Suggestion fatigue → novice ignores or distrusts the mechanism] → hard cap of one suggestion per session, offer-only posture, gold-signal weighting (correction of a domain fact) documented as the highest-precision trigger.
- [Stale domain skills asserting outdated data with confidence] → "verified on YYYY-MM" marker required for volatile data + the "won't self-update" warning baked into the standard message; automated monitoring explicitly deferred to v2.
- [Upstream `openspec update` overwrites hub surface clauses (D-B)] → same exposure as existing session-coordination sections; kit-owned skill (D-A) keeps guidance reachable regardless; re-apply hub clauses after upstream updates.
- [New skill adds its own per-session description cost — the very inflation it warns about] → single skill (not one per topic), description held to 1–2 sentences, dense text in the body only.
- [Installed repos' explore/propose surfaces carry no inline detection clause] → accepted v1 limitation of the ownership model; the skill description is written to trigger on the same signals, and v2 seed/harvest tooling can revisit.

## Migration Plan

Additive text-only change: new files + appended sections; no scripts, hooks, or CI behavior change. Deploy = merge; rollback = revert commit. `sdd-gates` continues to pass (`openspec validate --all --strict` sees only new/changed markdown; checksums regenerated before commit).

## Open Questions

None blocking v1. Deferred to v2 design (recorded in the spec delta): M5 threshold calibration, Cursor-side telemetry mechanism (no `PostToolUse` equivalent — degradation path required), harvest as separate skill vs `sdd-metrics.sh` extension.
